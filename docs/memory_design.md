# Memory Design

## 1. Зачем агенту нужна память

Память нужна, чтобы система не просто генерировала ответ, а могла сохранять историю запусков и использовать результаты работы агентов для анализа и отладки.

В ProductCase AI память используется для:

- сохранения идеи пользователя;
- сохранения промежуточных результатов агентов;
- сохранения итогового отчёта;
- возможности посмотреть прошлые запуски;
- объяснения работы системы на защите.

## 2. Типы памяти в системе

В проекте используются два типа памяти:

- краткосрочная память;
- долгосрочная память.

## 3. Краткосрочная память

Краткосрочная память существует только во время одного запуска системы.

Она реализована через состояние LangGraph.

В state хранятся:

- `trace_id`;
- `user_idea`;
- `plan`;
- `market_analysis`;
- `product_analysis`;
- `critic_review`;
- `final_report`.

Каждый агент получает текущее состояние, добавляет свой результат и передаёт состояние следующему агенту.

Пример:

User Idea → Planner Agent → `plan` → Market Analyst Agent → `market_analysis` → Product Manager Agent → `product_analysis` → Critic Agent → `critic_review` → Report Writer Agent → `final_report`

## 4. Долгосрочная память

Долгосрочная память сохраняется после завершения работы программы.

В ProductCase AI она реализована через SQLite.

Файл базы данных:

`app/memory/memory.db`

В таблицу `runs` сохраняются:

- id запуска;
- trace_id;
- исходная идея пользователя;
- план анализа;
- рыночный анализ;
- продуктовый анализ;
- критика;
- финальный отчёт;
- дата и время запуска.

## 5. Почему выбран SQLite

SQLite выбран для MVP, потому что:

- не требует отдельного сервера;
- хранит данные локально;
- легко запускается на любом компьютере;
- подходит для учебного прототипа;
- проще в настройке, чем PostgreSQL, Redis, Neo4j или векторная база;
- хорошо подходит для хранения истории запусков.

## 6. Почему не выбран классический RAG

Классический RAG обычно используется, когда системе нужно искать информацию в большой базе документов.

В текущем проекте основная задача другая: не поиск по документам, а пошаговая обработка одной продуктовой идеи несколькими агентами.

Поэтому классический RAG не является оптимальным вариантом для MVP.

Для ProductCase AI важнее хранить:

- ход выполнения;
- результаты агентов;
- историю запусков;
- отчёты.

Именно поэтому для первой версии выбрана SQLite-память и Markdown-контекст.

## 7. Рассмотренные альтернативы

### 7.1 Vector DB

Векторная база могла бы использоваться для поиска похожих прошлых идей или документов.

Минусы для MVP:

- сложнее настройка;
- нужен embedding pipeline;
- нужно хранить и обновлять индексы;
- для текущего прототипа это избыточно.

### 7.2 Graph memory

Графовая память могла бы хранить связи между продуктами, аудиториями, конкурентами и фреймворками.

Минусы для MVP:

- сложнее проектирование;
- нужна графовая база;
- больше времени на реализацию;
- не критично для первого рабочего прототипа.

### 7.3 Mem0 / Zep / Graphiti / Letta

Эти инструменты полезны для более продвинутой агентной памяти.

Но для учебного MVP они усложняют инфраструктуру:

- появляются дополнительные сервисы;
- требуется отдельная настройка;
- сложнее объяснять и защищать реализацию;
- выше риск не успеть собрать рабочую версию.

## 8. Markdown-файлы как семантическая память

Кроме SQLite, в проекте используются Markdown-файлы:

`app/skills/`

и

`app/knowledge/`

Они содержат правила поведения агентов и продуктовые знания.

Примеры:

- `product_vision_skill.md`;
- `jtbd_skill.md`;
- `lean_canvas_skill.md`;
- `backlog_skill.md`;
- `critic_skill.md`;
- `SOUL.md`;
- `PRODUCT_METHODS.md`;
- `EVALUATION_RULES.md`.

Это не память о прошлых запусках, а семантический контекст, который помогает агентам работать стабильнее.

## 9. Недостатки выбранного подхода

У SQLite + Markdown memory есть ограничения:

- система пока не ищет похожие прошлые идеи автоматически;
- нет semantic retrieval;
- нет графа связей между сущностями;
- память не обновляет поведение агента автоматически;
- нет персонализации под конкретного пользователя.

## 10. Что можно улучшить

В следующих версиях можно добавить:

- поиск похожих прошлых запусков;
- embedding-модель и векторное хранилище;
- graph memory для связей между продуктами и рынками;
- Mem0 или Zep как специализированный memory layer;
- summarization прошлых запусков;
- использование памяти при генерации новых отчётов.
