# Observability Guide

## 1. Зачем нужна observability

Observability нужна, чтобы понимать, как работает агентная система во время выполнения.

Для LLM-агентов это особенно важно, потому что нужно видеть:

- какой агент был вызван;
- в каком порядке работали агенты;
- сколько времени занял каждый этап;
- где произошла ошибка;
- какой запуск связан с каким отчётом;
- как отследить работу системы после завершения программы.

## 2. Что реализовано в ProductCase AI

В текущей версии реализована базовая observability через JSONL-логи.

Файл логов:

`logs/run_logs.jsonl`

Каждый запуск получает уникальный `trace_id`.

Этот `trace_id` используется в:

- логах;
- SQLite-памяти;
- имени отдельного отчёта;
- выводе в терминале.

## 3. Какие события логируются

Система сохраняет следующие события:

- `run_start` — старт запуска;
- `agent_start` — старт работы агента;
- `agent_end` — успешное завершение агента;
- `agent_error` — ошибка агента;
- `run_end` — завершение запуска.

## 4. Какие данные сохраняются в логах

Для каждого события сохраняются:

- тип события;
- timestamp;
- trace_id;
- имя агента, если событие связано с агентом;
- статус выполнения;
- длительность выполнения агента;
- текст ошибки, если она возникла.

## 5. Где реализованы логи

Логирование реализовано в файле:

`app/tools/observability_tool.py`

В нём есть функции:

- `write_log`;
- `log_run_start`;
- `log_run_end`;
- `run_with_observability`.

Функция `run_with_observability` оборачивает запуск каждого агента, измеряет время выполнения и записывает результат в лог.

## 6. Как observability подключена к агентам

В файле `app/graph.py` каждый агент вызывается через `run_with_observability`.

Например:

Planner Agent вызывается не напрямую, а через observability-обёртку.

Это позволяет не менять внутреннюю логику агента, но при этом фиксировать его запуск, завершение, время работы и ошибки.

## 7. Пример логов

Пример строки лога:

`{"event": "agent_end", "trace_id": "...", "agent_name": "Planner Agent", "status": "success", "duration_seconds": 12.431, "timestamp": "2026-05-08T12:00:00"}`

Такой формат удобен, потому что JSONL можно читать построчно, анализировать скриптами или подключить к внешним системам мониторинга.

## 8. Почему выбран JSONL

JSONL выбран для MVP, потому что:

- это простой формат;
- его легко читать;
- он не требует отдельного сервера;
- каждая строка является отдельным JSON-событием;
- подходит для локального прототипа;
- его можно потом отправлять в Loki, ELK, Grafana или другой стек.

## 9. Что можно мониторить в агентной системе

В агентной системе полезно отслеживать:

- количество запусков;
- успешные и неуспешные запуски;
- длительность работы каждого агента;
- количество ошибок;
- среднее время генерации;
- качество результатов по evals;
- изменение качества после правки prompts или skills;
- расход токенов, если модель/движок это поддерживает;
- частоту галлюцинаций;
- долю неполных ответов.

## 10. Рассмотренные альтернативы

### 10.1 Langfuse

Langfuse — специализированный инструмент для LLM observability.

Он позволяет отслеживать:

- traces;
- prompts;
- completions;
- latency;
- token usage;
- scores;
- user sessions.

Для MVP Langfuse не был подключён, чтобы не усложнять инфраструктуру. Но его можно добавить в следующей версии.

### 10.2 LangSmith

LangSmith хорошо подходит для проектов на LangChain/LangGraph.

Он помогает отслеживать цепочки вызовов, тестировать prompts и анализировать поведение LLM-приложений.

Минус для текущего проекта — зависимость от внешнего сервиса.

### 10.3 Prometheus и Grafana

Prometheus и Grafana подходят для мониторинга метрик:

- latency;
- количество запросов;
- ошибки;
- загрузка сервиса.

Для учебного MVP это избыточно, но такой стек можно подключить при развитии проекта.

## 11. Недостатки текущего подхода

У текущей observability есть ограничения:

- нет визуального dashboard;
- нет алертинга;
- нет автоматического подсчёта метрик;
- нет token usage;
- нет трассировки prompts/completions в отдельной системе;
- логи нужно смотреть вручную.

## 12. Возможные улучшения

В следующих версиях можно добавить:

- Langfuse для LLM tracing;
- Prometheus для метрик;
- Grafana для dashboard;
- алерты при ошибках;
- подсчёт средней длительности агентов;
- сохранение token usage;
- связь eval scores с конкретными trace_id;
- dashboard по качеству работы системы.
