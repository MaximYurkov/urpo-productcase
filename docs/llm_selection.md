# LLM Selection

## 1. Задача выбора LLM

Для ProductCase AI нужно было выбрать локальную open-source LLM, которая может работать на доступном железе и выполнять задачи продуктового анализа.

Модель должна уметь:

- понимать описание продуктовой идеи;
- отвечать на русском языке;
- работать с инструкциями;
- формировать структурированный текст;
- поддерживать многошаговый workflow;
- не требовать облачного API.

## 2. Что такое LLM

LLM, или Large Language Model, — это большая языковая модель, которая обучена предсказывать и генерировать текст на основе контекста.

В агентной системе LLM используется как reasoning engine: она получает инструкцию, входные данные и генерирует результат для конкретного агента.

## 3. Что значит B в названии модели

Буква `B` означает billion, то есть миллиард параметров.

Например:

- 1.5B — примерно 1.5 миллиарда параметров;
- 2B — примерно 2 миллиарда параметров;
- 7B — примерно 7 миллиардов параметров.

Чем больше параметров, тем обычно выше качество рассуждений, но тем больше модель требует памяти и вычислительных ресурсов.

## 4. Рассмотренные движки для локального запуска

### 4.1 Ollama

Плюсы:

- простой запуск;
- удобная установка моделей;
- есть Docker-вариант;
- понятный API на `localhost:11434`;
- хорошо подходит для учебного проекта;
- поддерживает много open-source моделей.

Минусы:

- меньше возможностей для production-оптимизации, чем у vLLM;
- производительность зависит от железа;
- на CPU генерация может быть медленной.

### 4.2 llama.cpp

Плюсы:

- очень лёгкий и быстрый движок;
- хорошо работает с GGUF-моделями;
- подходит для слабого железа.

Минусы:

- менее удобен для быстрого прототипирования;
- нужно отдельно разбираться с форматами моделей;
- интеграция требует больше ручной настройки.

### 4.3 vLLM

Плюсы:

- высокая производительность;
- хорошо подходит для серверного inference;
- умеет эффективно обслуживать много запросов.

Минусы:

- более тяжёлая инфраструктура;
- больше требований к GPU;
- избыточен для локального учебного MVP.

## 5. Почему выбран Ollama

Для MVP выбран Ollama, потому что он проще всего закрывает задачу локального запуска LLM.

Причины выбора:

- быстро поднимается через Docker Compose;
- не требует облачного API;
- легко менять модели;
- есть поддержка популярных open-source LLM;
- хорошо интегрируется с LangChain через `langchain-ollama`;
- подходит для демонстрации локального агентного workflow.

## 6. Какие модели рассматривались

Для проекта рассматривались лёгкие модели, которые можно запустить локально:

### 6.1 qwen2.5:1.5b

Плюсы:

- лёгкая модель;
- запускается на обычном компьютере;
- неплохо понимает русский язык;
- подходит для MVP;
- быстро скачивается и не требует много памяти.

Минусы:

- иногда даёт слабые формулировки;
- может обрывать длинный ответ;
- хуже справляется со сложными рассуждениями, чем более крупные модели;
- может смешивать русский и английский язык.

### 6.2 llama3.2:1b

Плюсы:

- очень лёгкая;
- быстро работает;
- подходит для простых задач.

Минусы:

- слабее в структурированных длинных ответах;
- хуже работает с русским языком;
- чаще требует уточняющих промптов.

### 6.3 gemma2:2b

Плюсы:

- лёгкая модель;
- хорошее качество для своего размера;
- может использоваться для простых агентных задач.

Минусы:

- может хуже отвечать на русском;
- на части железа может работать медленнее;
- требует проверки качества на конкретных задачах.

## 7. Итоговый выбор

Для MVP выбрана модель:

`qwen2.5:1.5b`

Причины выбора:

- запускается локально через Ollama;
- работает на доступном железе;
- поддерживает русский язык;
- достаточно лёгкая для тестов;
- подходит для демонстрации мультиагентной архитектуры;
- модель можно заменить без изменения архитектуры проекта.

## 8. Критерии выбора модели

Модели сравнивались по следующим критериям:

- возможность локального запуска;
- скорость генерации;
- качество русского языка;
- следование инструкциям;
- качество структурированных ответов;
- склонность к галлюцинациям;
- стабильность при длинных ответах;
- требования к ресурсам.

## 9. Галлюцинации

Галлюцинации — это ситуация, когда LLM генерирует уверенный, но неверный или неподтверждённый ответ.

В ProductCase AI это особенно важно для разделов:

- конкуренты;
- рынок;
- целевая аудитория;
- риски.

Чтобы снизить риск галлюцинаций, в prompts и skills указано:

- если точных данных нет, писать, что это гипотеза;
- не выдавать рыночные предположения как факт;
- использовать Critic Agent для проверки слабых мест;
- фиксировать ограничения MVP в документации.

## 10. Контекстное окно

Контекстное окно — это объём текста, который модель может учитывать при генерации ответа.

На него влияет:

- длина system prompt;
- длина user input;
- результаты предыдущих агентов;
- skills и knowledge-файлы;
- длина итогового отчёта.

Если контекст слишком большой, модель может хуже следовать инструкции или обрывать ответ.

Поэтому в проекте:

- prompts сделаны относительно короткими;
- skills разделены по файлам;
- агенты работают по этапам;
- длина генерации ограничена через `num_predict`.

## 11. Ограничения выбранной модели

Главное ограничение `qwen2.5:1.5b` — это небольшой размер.

Из-за этого модель может:

- давать менее глубокие рассуждения;
- писать слишком общие формулировки;
- частично переходить на английский;
- обрывать длинные ответы;
- хуже проверять фактическую точность.

Это ограничение принято осознанно, потому что цель MVP — показать архитектуру мультиагентной системы, а не получить качество уровня крупных облачных моделей.

## 12. Возможные улучшения

В следующих версиях можно попробовать:

- Qwen более крупного размера;
- Llama 3.1/3.2 большего размера;
- Mistral;
- Gemma;
- Kimi;
- GLM;
- MiniMax.

Также можно сделать так, чтобы разные агенты использовали разные модели:

- лёгкая модель для Planner Agent;
- более сильная модель для Product Manager Agent;
- отдельная модель для Critic Agent.
