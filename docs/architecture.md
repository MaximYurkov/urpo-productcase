# Архитектура ProductCase AI

## 1. Общий подход

ProductCase AI построен как мультиагентная LLM-система с последовательным workflow.

В проекте используется не один большой промпт, а несколько специализированных агентов. Каждый агент отвечает за отдельный этап анализа продуктовой идеи.

Общий процесс:

User Input → Planner Agent → Market Analyst Agent → Product Manager Agent → Critic Agent → Report Writer Agent → Markdown Report

## 2. Почему выбран workflow-подход

Для проекта рассматривались два основных паттерна мультиагентной архитектуры:

- Supervisor pattern;
- Workflow / choreography pattern.

Supervisor pattern подходит для систем, где пользовательские запросы сильно отличаются друг от друга и нужно динамически выбирать, какого агента вызвать.

В ProductCase AI задача более стабильная: любая продуктовая идея должна пройти одни и те же этапы анализа:

- планирование;
- анализ рынка и пользователей;
- продуктовая проработка;
- критика;
- сборка отчёта.

Поэтому выбран workflow-подход. Он проще, предсказуемее и лучше подходит для учебного MVP, потому что гарантирует прохождение всех обязательных этапов.

## 3. Основные компоненты системы

### 3.1 CLI-интерфейс

Пользователь запускает проект через команду:

`python -m app.main`

После этого он вводит продуктовую идею в терминале.

### 3.2 LangGraph workflow

LangGraph используется для описания графа выполнения агентов.

Файл:

`app/graph.py`

В нём задаются:

- состояние системы;
- узлы графа;
- порядок вызова агентов;
- передача данных между агентами.

### 3.3 Агенты

Агенты находятся в папке:

`app/agents/`

Состав агентов:

- `planner.py`;
- `market_analyst.py`;
- `product_manager.py`;
- `critic.py`;
- `report_writer.py`.

Каждый агент имеет отдельную функцию запуска, отдельный system prompt и свою зону ответственности.

### 3.4 LLM-движок

Для запуска модели используется Ollama.

Ollama поднят через Docker Compose и доступен по адресу:

`http://localhost:11434`

Основная модель MVP:

`qwen2.5:1.5b`

### 3.5 Skills

Skills хранятся в Markdown-файлах:

`app/skills/`

Они используются как дополнительный контекст для агентов.

Примеры skills:

- `product_vision_skill.md`;
- `jtbd_skill.md`;
- `lean_canvas_skill.md`;
- `backlog_skill.md`;
- `critic_skill.md`.

Загрузка skills реализована через:

`app/tools/skill_loader.py`

### 3.6 Память

Память реализована через SQLite.

Файл базы:

`app/memory/memory.db`

В память сохраняются:

- trace_id запуска;
- исходная идея пользователя;
- результаты каждого агента;
- финальный отчёт;
- дата и время запуска.

### 3.7 Observability

Наблюдаемость реализована через JSONL-логи.

Файл логов:

`logs/run_logs.jsonl`

Логируются:

- старт запуска;
- завершение запуска;
- старт каждого агента;
- завершение каждого агента;
- длительность работы агента;
- ошибки.

### 3.8 Evals

Оценка системы реализована в:

`evals/run_evals.py`

Тестовые кейсы находятся в:

`evals/test_cases.json`

Результаты сохраняются в:

`evals/eval_results.json`

## 4. Состояние системы

Во время запуска LangGraph передаёт между агентами общее состояние.

Состояние содержит:

- `trace_id`;
- `user_idea`;
- `plan`;
- `market_analysis`;
- `product_analysis`;
- `critic_review`;
- `final_report`.

Каждый агент получает состояние, добавляет в него свой результат и передаёт дальше.

## 5. Последовательность работы

1. Пользователь вводит идею продукта.
2. `main.py` создаёт `trace_id`.
3. Записывается событие `run_start`.
4. Создаётся LangGraph workflow.
5. Planner Agent формирует план анализа.
6. Market Analyst Agent анализирует рынок и пользователей.
7. Product Manager Agent формирует продуктовую часть.
8. Critic Agent проверяет результат.
9. Report Writer Agent собирает итоговый Markdown-отчёт.
10. Отчёт сохраняется в папку `reports/`.
11. Данные запуска сохраняются в SQLite.
12. Записывается событие `run_end`.

## 6. Почему это мультиагентная система

В системе используется одна локальная LLM, но на её основе реализованы разные агенты.

Агенты отличаются:

- ролью;
- system prompt;
- входными данными;
- skill-файлами;
- местом в workflow;
- результатом, который они возвращают.

Это не один промпт, потому что каждый этап выполняется отдельным агентом, а результаты передаются через общее состояние LangGraph.

## 7. Ограничения архитектуры

Текущая версия является MVP.

Ограничения:

- используется фиксированный workflow без динамического роутинга;
- нет critic-loop для автоматической доработки результата;
- нет веб-интерфейса;
- нет внешнего поиска;
- память реализована через SQLite, без графовой БД;
- observability реализована локально, без Langfuse или Grafana.

## 8. Возможные улучшения архитектуры

В следующих версиях можно добавить:

- supervisor/router agent;
- critic-loop;
- Streamlit или FastAPI интерфейс;
- Langfuse для LLM-tracing;
- Prometheus и Grafana;
- graph memory;
- vector search;
- web search tool для проверки конкурентов.
