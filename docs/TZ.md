# Техническое задание

## 1. Название проекта

ProductCase AI — мультиагентная LLM-система для подготовки продуктового кейса.

## 2. Назначение системы

ProductCase AI предназначен для помощи студентам и начинающим продакт-менеджерам в анализе продуктовой идеи.

Система принимает на вход краткое описание идеи продукта и с помощью нескольких специализированных агентов формирует структурированный продуктовый кейс.

## 3. Проблема

При подготовке продуктового кейса студенту нужно разложить идею по нескольким направлениям:

- описать проблему пользователя;
- определить целевую аудиторию;
- сформулировать JTBD;
- подготовить Lean Canvas;
- описать MVP;
- составить backlog;
- предложить roadmap;
- определить риски;
- критически проверить результат.

Если делать это вручную, легко пропустить важные разделы или получить несвязанный текст. Поэтому в проекте используется мультиагентный подход: каждый агент отвечает за отдельный этап анализа.

## 4. Цель проекта

Разработать рабочий прототип мультиагентной LLM-системы, которая помогает пользователю проанализировать продуктовую идею и сформировать структурированный Markdown-отчёт.

## 5. Пользователь системы

Основной пользователь — студент, начинающий продакт-менеджер или участник учебного проекта, которому нужно быстро подготовить черновик продуктового кейса для дальнейшей доработки.

## 6. Входные данные

Пользователь вводит текстовое описание продуктовой идеи.

Пример входа:

AI-сервис для автоматического подбора рекламных креативов для малого бизнеса. Пользователь загружает описание товара или услуги, а система предлагает идеи баннеров, тексты объявлений и рекомендации по аудитории для рекламы во ВКонтакте и Яндекс Директ.

## 7. Выходные данные

Система формирует Markdown-отчёт в папке `reports/`.

Результат содержит:

- идею продукта;
- план анализа;
- рыночный и пользовательский анализ;
- продуктовую проработку;
- JTBD;
- Lean Canvas;
- MVP;
- backlog;
- roadmap;
- риски;
- критику и рекомендации.

Также система сохраняет:

- лог запуска в `logs/run_logs.jsonl`;
- историю запуска в SQLite-память `app/memory/memory.db`;
- отдельный отчёт запуска в `reports/report_<trace_id>.md`;
- последний отчёт в `reports/generated_report.md`.

## 8. Состав агентов

В системе используются пять агентов.

### 8.1 Planner Agent

Отвечает за первичный разбор идеи и составление плана анализа.

Задачи:

- понять суть продуктовой идеи;
- определить, какие аспекты нужно проанализировать;
- подготовить план для следующих агентов.

### 8.2 Market Analyst Agent

Отвечает за рыночный и пользовательский анализ.

Задачи:

- определить проблему пользователя;
- описать целевую аудиторию;
- выделить пользовательские сегменты;
- предположить конкурентов;
- определить рыночные риски.

### 8.3 Product Manager Agent

Отвечает за продуктовую часть кейса.

Задачи:

- сформулировать продуктовую ценность;
- описать JTBD;
- подготовить Lean Canvas;
- определить MVP;
- составить backlog;
- предложить roadmap.

### 8.4 Critic Agent

Отвечает за проверку результата.

Задачи:

- найти логические слабости;
- выявить слишком общие утверждения;
- отметить возможные галлюцинации;
- предложить улучшения.

### 8.5 Report Writer Agent

Отвечает за сборку итогового отчёта.

Задачи:

- собрать результаты всех агентов;
- оформить результат в Markdown;
- сохранить отчёт в папку `reports/`.

## 9. Архитектура системы

Система построена как последовательный workflow на LangGraph.

Общий процесс:

User Input → Planner Agent → Market Analyst Agent → Product Manager Agent → Critic Agent → Report Writer Agent → Markdown Report

В проекте выбран workflow-подход, потому что задача подготовки продуктового кейса имеет стабильную последовательность этапов. Для такого типа задачи важно, чтобы идея прошла все обязательные шаги анализа.

## 10. Используемый стек

- Python — основной язык реализации.
- Ollama — локальный запуск open-source LLM.
- qwen2.5:1.5b — основная локальная модель для MVP.
- LangGraph — построение мультиагентного workflow.
- SQLite — долгосрочное хранение истории запусков.
- Markdown-файлы — skills и semantic knowledge.
- Docker Compose — изолированный запуск Ollama.
- JSONL-логи — базовая observability.
- Git — контроль версий.

## 11. Память системы

В системе используются два уровня памяти.

### 11.1 Краткосрочная память

Краткосрочная память хранится в состоянии LangGraph во время одного запуска.

Она содержит:

- исходную идею;
- план;
- рыночный анализ;
- продуктовый анализ;
- критику;
- финальный отчёт.

### 11.2 Долгосрочная память

Долгосрочная память реализована через SQLite.

В базу сохраняются:

- trace_id запуска;
- идея пользователя;
- результаты агентов;
- итоговый отчёт;
- дата и время запуска.

## 12. Skills и knowledge-файлы

Для агентов созданы отдельные skill-файлы в папке `app/skills/`.

Примеры:

- `product_vision_skill.md`;
- `jtbd_skill.md`;
- `lean_canvas_skill.md`;
- `backlog_skill.md`;
- `critic_skill.md`.

Эти файлы используются агентами как дополнительный контекст и правила поведения.

Также предусмотрена папка `app/knowledge/`, где хранятся семантически наполненные Markdown-файлы:

- `SOUL.md`;
- `PRODUCT_METHODS.md`;
- `EVALUATION_RULES.md`.

## 13. Изоляция

Для изоляции используется Docker Compose.

В Docker запускается Ollama — локальный движок для LLM. Это позволяет:

- изолировать LLM-движок от основной системы;
- упростить запуск проекта;
- сделать окружение более воспроизводимым;
- не зависеть от облачных LLM API.

## 14. Observability

В проекте реализована базовая наблюдаемость.

Система сохраняет:

- `trace_id` каждого запуска;
- старт и завершение запуска;
- старт и завершение каждого агента;
- длительность работы каждого агента;
- ошибки, если они возникают.

Логи сохраняются в файл `logs/run_logs.jsonl`.

## 15. Evals

Для оценки качества работы системы реализован скрипт `evals/run_evals.py`.

Он запускает систему на нескольких тестовых идеях и проверяет наличие ключевых блоков в результатах агентов.

Оцениваются:

- наличие анализа аудитории;
- наличие JTBD;
- наличие Lean Canvas;
- наличие MVP;
- наличие backlog;
- наличие roadmap;
- наличие рисков;
- наличие критики.

Результаты сохраняются в файл `evals/eval_results.json`.

## 16. Ограничения MVP

Проект является учебным прототипом, поэтому имеет ограничения:

- используется лёгкая локальная модель, поэтому качество текста может быть ниже, чем у крупных облачных моделей;
- система не использует реальный веб-поиск;
- конкуренты и рыночные выводы формируются как гипотезы;
- observability реализована через локальные JSONL-логи, без полноценного production-мониторинга;
- память реализована через SQLite, без графовой базы знаний или векторного хранилища.

## 17. Возможные улучшения

В дальнейшем систему можно развить:

- подключить более сильную LLM;
- добавить web-интерфейс;
- подключить Langfuse для LLM-native observability;
- добавить Prometheus и Grafana для метрик;
- добавить векторную или графовую память;
- реализовать critic-loop, где Critic Agent может возвращать задачу на доработку;
- добавить веб-поиск для проверки конкурентов и рынка;
- расширить evals более сложными метриками.
